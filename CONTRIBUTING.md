# Участие в проекте

Спасибо за интерес! Проект небольшой, правила простые.

## Окружение

```bash
git clone https://github.com/saniq7/RetailCRM-MG-Connector.git
cd RetailCRM-MG-Connector
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
```

## Перед пуш-реквестом

```bash
pytest          # тесты
ruff check .    # линтер
```

Оба должны быть зелёными — это же проверяет CI.

## Правила кода

- **Только стандартная библиотека** в рантайме. Внешние пакеты допустимы
  исключительно как dev-зависимости.
- **Никаких сетевых запросов в тестах.** Используйте `FakeHttp` из
  `tests/fakes.py` — он реализует интерфейс `HttpClient`.
- **Секреты не печатаются целиком.** Для любого вывода — `config.mask()`.
  Если добавляете новый параметр в URL, проверьте, что `_redact()` его скроет.
- **Ленивые итераторы** для листингов: пользователь может запросить 5 элементов
  из миллиона.
- Стиль: `ruff` с настройками из `pyproject.toml`, длина строки 100.
- Комментарии и docstrings — на русском, как в остальном коде.

## Что особенно пригодится

- Новые пути к токену в ответе RetailCRM: если у вашей версии CRM поле лежит
  иначе, добавьте путь в `TOKEN_PATHS` и тест к нему.
- Поддержка методов MG, которых ещё нет: отправка сообщений, webhooks.
- Примеры интеграций в `examples/`.

## Оформление изменений

- Одна ветка — одна задача.
- Сообщение коммита: короткая строка в повелительном наклонении, при
  необходимости — абзац с объяснением «почему».
- В описании PR: что изменилось, зачем, как проверяли.

## Версионирование и выпуск

Проект следует [семантическому версионированию](https://semver.org/lang/ru/).

| Часть | Когда растёт |
|---|---|
| **MAJOR** | Несовместимые изменения CLI, переменных окружения или публичного API |
| **MINOR** | Новые команды и возможности без ломки существующих |
| **PATCH** | Исправления, не меняющие поведение |

Публичным API считаются команды и флаги `retailcrm-mg`, переменные `RETAILCRM_*`,
классы `Config`, `MgClient`, `RetailCrmClient` и функции модуля `export`.
Всё, что начинается с подчёркивания, — внутреннее и может меняться в любом выпуске.

Версия живёт в одном месте — `src/retailcrm_mg/__init__.py`; `pyproject.toml`
читает её оттуда, дублировать не нужно.

Порядок выпуска:

1. Поднять `__version__`.
2. Добавить раздел в `CHANGELOG.md` — CI берёт из него описание релиза.
3. Смержить в `main`.
4. Поставить тег и запушить:
   ```bash
   git tag -a v1.2.3 -m "v1.2.3"
   git push origin v1.2.3
   ```

Тег запускает workflow `Release`: он прогоняет тесты и линтер, проверяет,
что тег совпадает с `__version__`, собирает пакет и публикует GitHub Release.
Расхождение версии и тега останавливает выпуск.
